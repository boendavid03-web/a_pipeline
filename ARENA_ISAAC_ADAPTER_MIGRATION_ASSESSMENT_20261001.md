## 4. Robot, LiDAR, HuNav migration cost

**Robot:** Jackal source Xacro already declares four wheel velocity command interfaces and joint names; live control YAML uses 0.36 m separation × 1.5 multiplier and 0.098 m radius. Its current `ros2_control` hardware plugin is GazeboSystem (or JackalHardware/GenericSystem outside simulation), not the official adapter's external joint-state-topic hardware architecture. The isolated adapter publishes/consumes joint command/state topics and builds separate odom/TF graphs. A direct switch would need a generated URDF hardware-plugin mapping, controller manager, topic bridge, wheel calibration, and single-publisher odom/TF proof while preserving `cmd_vel_nav → smoother → collision monitor → cmd_vel`. **It cannot directly replace the current Jackal control without further work and parity tests.**

**LiDAR:** The official parser reads the Jackal source's 640 horizontal samples, 16 vertical channels, ±π horizontal FOV, 0.08–12 m range and 10 Hz nominal rate. It creates a 3D point prim plus a separate one-line, zero-elevation LaserScan prim and publishes under the configured topic/frame. This can express the current 640-beam benchmark contract on paper; actual beam order, finite ranges, rate, frame `jackal/lidar_link`, topic, and local/global costmap response still require a paired runtime bag. The frozen default bag's median scan header interval was about 0.217 sim seconds, so a nominal 10 Hz configuration is not sufficient acceptance.

**HuNav:** Keep current `ComputeAgents`, robot odom input, configured behavior, three agent names, velocity/yaw, and Isaac as the sole pose/animation/collision writer. A shim can map numeric names to a stable `pedestrians/_N` namespace; spawn once, send exact pose and orientation at each HuNav tick, check result codes, read back named state, then delete/reset on episode boundary. The official `MovePedestrians` does exact pose updates but does not consume HuNav velocity for interpolation; `UpdatePedestrians` consumes twist/stamp and extrapolates. No equivalent behavior-state field or built/generated `arena_people_msgs` contract was available for a complete mapping. Those are prerequisites, not assumptions of compatibility.
